# 씬 저장 상태와 모달 대화상자

**로드 조건**: 씬 저장·전환, `run_tests`·플레이모드 진입, 열린 씬 수정 작업이거나, 모달 대화상자·도메인 리로드 중 타임아웃이 생겼을 때 이 문서를 읽는다. 상위 지침 문서 §2.0.5의 요약 4줄은 이 문서를 읽기 전에도 항상 적용된다.

이 문서는 상위 지침 문서(프로젝트 루트: `AGENTS.md`/`CLAUDE.md`, .unity-kb 원본: `HARNESS.md`) §1~4의 행동 규칙 아래에서 적용되는 도메인 절차다. 충돌 시 그 문서(§0~4)가 우선한다. 본문의 절 번호(§1.3, §1.4, §2.0.1, §2.0.3 등)는 상위 지침 문서를 가리킨다.

## 기본 원칙
- **팝업을 닫는 것보다 팝업이 생기는 작업 순서를 없애는 것이 우선이다.**
- 테스트 편의보다 사용자 변경 보존이 우선이다. 명시적인 씬 저장·전환·플레이 진입 금지 지시는 이 절의 절차보다 우선한다.
- 모달 대화상자는 Editor 메인 스레드를 점유하여 `editor_status`를 포함한 live 명령을 지연시키거나 타임아웃시킬 수 있다. 그러나 빈 응답이나 `"Main thread operation timed out"`만으로 모달 발생 또는 작업 코드 오류를 단정하지 않는다.
- 모달 감지, 버튼 실행, 저장 성공 확인은 별도 단계다. 창이 닫혔다는 사실만으로 저장 또는 작업 성공을 보고하지 않는다.

## 시작 전 상태 확인과 기존 변경 보존
- 열린 모든 씬의 경로·`isDirty`, 활성 씬, 플레이·컴파일·도메인 리로드 상태를 live 채널로 확인한다. 대상 씬뿐 아니라 다른 열린 씬의 미저장 상태도 확인한다.
- `isDirty`는 저장 필요 상태를 나타내며 실제 직렬화 내용 차이와 항상 일치하지는 않는다. 다만 `isDirty == true`이면 미저장 변경이 있을 수 있는 것으로 취급한다.
- 디스크/Git diff는 Editor 메모리의 미저장 상태를 보여주지 않는다. 메모리 상태와 디스크 사본을 비교하더라도 변경 주체까지 판정할 수는 없다.
- 시작 시 미저장 변경은 사용자와 보존 방식을 합의하기 전까지 임의로 저장하거나 버리지 않는다. 비교를 위해 원본 씬에 덮어쓰거나, 저장·재로드로 dirty 상태를 제거하지 않는다.
- Editor를 다른 세션이 함께 사용할 수 있다. 시작 당시 clean이었다는 사실만으로 이후 변경이 모두 내 변경이라고 간주하지 않는다. 저장·전환·테스트 직전에 상태를 다시 확인하고, 예상하지 못한 변경이 있으면 중단한다.

## 열린 씬 수정과 저장
- **열린 `.unity` 파일에는 파일 패치를 하지 않는다.** 열린 씬은 live API로만 수정하고 Undo·변경 추적을 등록한다(§2.0.3). 디스크와 메모리 상태를 어긋나게 하여 리로드 확인창을 유발하지 않는다.
- 닫힌 씬 파일을 수정할 때도 먼저 해당 씬이 열려 있지 않은지 확인한다.
- 씬 저장이 승인된 작업이고 기존 미저장 변경을 함께 저장할 위험이 해소된 경우에만, 변경한 대상 씬을 저장한다. 씬 저장은 AI 변경만이 아니라 해당 씬의 미저장 변경 전체를 저장한다는 점에 유의한다.
- 저장에는 현재 버전에서 확인된 대상 씬 저장 명령 또는 `EditorSceneManager.SaveScene(scene)`을 사용한다. `save_all`은 사용하지 않는다.
- 기존 씬은 원래 경로에 저장하고 반환값, 씬 경로, `isDirty == false`를 확인한다. 경로 없는 씬은 저장 경로를 확정하기 전에 저장 명령을 실행하지 않는다.
- 파일 사본이나 임시 씬을 이용한 보존이 필요하면 그 방식과 경로를 먼저 합의한다. 임의 복제·전환을 우회 수단으로 도입하지 않는다.

## 코드와 씬 작업 순서
- 코드와 씬을 함께 변경할 때는 다음 순서로 진행한다.
  1. `.cs` 변경
  2. live 채널로 반영
  3. 컴파일·도메인 리로드 종료와 Editor `ready` 확인
  4. 씬 변경
  5. 저장 조건을 충족한 경우 대상 씬 저장
  6. 결과 검증
- 컴파일을 일으킬 수 있는 명령과 씬 조작은 병렬로 실행하지 않는다. 서로 독립적인 정적 파일 조회는 병렬 실행해도 된다.
- Pipeline의 씬 저장 명령이 내부에서 `AssetDatabase.Refresh()`를 호출할 수 있다. 현재 연결된 버전의 구현·문서에서 확인하며, Unity의 `EditorSceneManager.SaveScene()` 자체와 래퍼 명령의 동작을 혼동하지 않는다.
- 이미 반영·검증된 변경에 Refresh·재컴파일을 습관적으로 중복 호출하지 않는다. 추가 파일 변경 또는 반영 누락의 근거가 있을 때만 다시 실행한다.

## 씬 전환과 테스트·플레이 진입
- 대상 씬이 이미 열려 있으면 다시 열지 않는다. 씬 전환이 필요하면 열린 모든 씬의 미저장 상태와 보존 방식을 먼저 확인한다.
- `open_scene` 등 씬 전환 명령이 저장 확인창을 보여준다고 가정하지 않는다. API·Pipeline 구현에 따라 미저장 변경이 확인 없이 사라질 수 있다.
- 단순 표시·설정·조건 변경은 기초 검증으로 끝내며, 확인을 위해 불필요하게 씬을 전환하거나 플레이모드에 진입하지 않는다.
- `run_tests` 또는 플레이모드 진입 전에는 다음을 확인한다.
  - 열린 모든 씬의 미저장 상태
  - 테스트가 씬 전환·플레이 진입·씬 저장을 수행하는지 여부
  - 테스트 종료 후 현재 씬과 사용자 변경이 보존되는지 여부
- 테스트 실행을 이유로 기존 사용자 변경을 자동 저장하지 않는다. 저장 확인창이 예상되는데 보존 방식이 합의되지 않았다면 실행 전에 중단한다.
- EditMode 테스트라도 실행 방식에 따라 저장 확인창이 발생할 수 있다. 테스트 이름이나 분류만으로 안전하다고 판단하지 않는다.
- 테스트 상태 확인에 모달 감지를 포함하려면 사전 승인된 관측 수단을 사용한다. 모달이 점유한 메인 스레드에 의존하는 live 명령만으로 모달 감지·해제가 가능하다고 가정하지 않는다.
- 테스트 실행 자체를 승인받았더라도 예상하지 못한 대화상자의 자동 저장·폐기까지 승인받은 것으로 간주하지 않는다.

## 타임아웃과 리로드 중 연결 오류
- 도메인 리로드 중에는 Pipeline 서버나 진행 중 요청의 연결이 끊길 수 있다. 연결 오류만으로 코드 오류 또는 명령의 적용 여부를 판정하지 않는다.
- 타임아웃 뒤에도 변경이 이미 반영됐을 수 있으므로 변경 명령을 즉시 다시 보내지 않는다.
- 리로드 진행이 확인된 경우에만 정해진 제한 시간과 횟수 내에서 상태를 확인한다. `ready` 복귀 후 실제 씬·오브젝트·파일 상태를 조회하고 재시도 필요 여부를 판단한다.
- 빈 응답·원인 불명의 연결 실패를 리로드라고 가정하여 반복 폴링하지 않는다. 결과 확인 불가 시 §2의 검증 원칙과 §1.3의 재시도 한계에 따라 중단·보고한다.
- 타임아웃 로그를 임의로 삭제하거나 무시하여 검증 통과로 처리하지 않는다. 확인된 원인과 코드 검증 결과를 구분하여 보고한다.

## 모달이 발생했을 때
- 모달이 확인되면 후속 변경 명령을 보내지 않는다. 가능한 범위에서 Unity 프로세스 소유 창인지, 창 제목·내용·버튼·관련 씬을 확인하여 기록한다.
- OS 창 조회·버튼 조작은 §2.0.1의 live 채널 원칙에 대한 예외다. **이 절 자체는 예외를 자동 승인하지 않는다.** 필요하면 사용할 도구, 읽기 전용 감지인지 버튼 실행인지, 적용 범위를 설명하고 승인을 받는다.
- 저장 확인창의 자동 Save는 다음 조건을 모두 충족할 때만 허용한다.
  - 자동 해제 방식이 사전 승인되어 있다.
  - Unity 프로세스 소유 창이며 저장 확인창임을 확인했다.
  - 저장 대상과 경로가 확정되어 있다.
  - 기존 사용자·다른 세션의 미저장 변경을 보존하는 문제가 해소되어 있다.
  - 창이 저장할 모든 대상에 대해 저장 승인이 있다.
  - Save 버튼을 명시적으로 식별하여 실행할 수 있다.
- `EnumWindows`로 찾은 창에 `SetForegroundWindow` 후 Enter를 보내는 방식은 사용하지 않는다. 창 제목 일치나 포커스 전환 요청만으로 대상 창·기본 버튼을 신뢰하지 않는다.
- `"Don't Save"`는 이 자동화 절차에서 사용하지 않는다. 변경 폐기는 별도의 명시적 사용자 지시가 있어야 한다.
- 사용자나 다른 세션의 변경이 섞였을 가능성이 있는 경우, 디스크 변경에 따른 리로드 확인창, 처음 보는 창, 대상·버튼을 확실히 식별하지 못한 창은 자동 조작하지 않는다. §1.4 서식으로 보고하고 멈춘다.
- 버튼 실행 후에는 창 닫힘, Editor `ready`, 해당 씬의 경로·dirty 상태 및 저장 결과를 확인한다. `IsWindow(hwnd) == false`만으로 저장 성공을 판정하지 않는다.
- 보고에는 창 제목, 수행한 조작, 영향받은 씬, 확인된 결과와 미검증 항목을 남긴다.

## 기본 해결책으로 사용하지 않는 방법
- Auto Refresh 또는 Domain Reload의 전역 비활성화는 기본 해결책으로 사용하지 않는다. 반영 누락·런타임 상태 잔존 등 별도 문제가 생길 수 있다.
- 모달을 피하기 위한 무조건 저장, 미저장 변경 폐기, Editor 강제 종료, 씬 강제 재로드를 수행하지 않는다.
- 자동화가 막혔다는 이유로 별도 검증 시스템이나 창 제어 도구를 임의로 도입하지 않는다. 필요한 경우 §1의 승인 게이트를 따른다.
