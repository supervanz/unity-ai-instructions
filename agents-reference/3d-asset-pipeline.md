# 3D 에셋 생성 검증 절차

**로드 조건**: 3D 모델을 새로 생성하거나 씬에 배치하는 작업일 때만 이 문서를 읽는다. 프리미티브(Cube/Plane 등)만으로 구조/건축 요소를 배치하는 작업, 또는 이미 있는 에셋/패키지를 붙이는 작업에는 이 문서가 필요 없다. 레퍼런스 이미지 한 장으로 씬 전체(공간 구조+배치+카메라)를 재구성하는 작업이면 [scene-from-reference-image.md](scene-from-reference-image.md)가 진입점이다 — 이 문서는 그쪽에서 "생성형 메시가 필요하다"고 정해진 개별 오브젝트부터 적용한다.

이 문서는 상위 지침 문서(프로젝트 루트: `AGENTS.md`/`CLAUDE.md`, .unity-kb 원본: `HARNESS.md`) §1~4의 행동 규칙 아래에서 적용되는 도메인 절차다. 충돌 시 그 문서(§0~4)가 우선한다.

**v6 변경**: [scene-from-reference-image.md](scene-from-reference-image.md) 신설에 따라 그 문서와의 경계를 명시했다. ① 로드 조건에 씬 전체 재구성 작업은 그 문서가 진입점이라는 교차 참조를 추가했다. ② "적용 대상 판단" 절 상단에 같은 교차 참조를 추가했다. ③ "씬 배치 규약"의 적용 범위가 `model3d-tripo-p1` 인물에 국한되지 않고, 방향성이 있는 모든 생성 메시(소파 등 비대칭 가구 포함)에 적용됨을 명시했다 — 실측 근거는 소파를 회전 미검증(identity) 상태로 배치해 180도 뒤집힌 채 완료 보고한 사례([scene-from-reference-image.md](scene-from-reference-image.md) §5).

**v2 변경**: §0(도구 및 파이프라인 수단 구분)을 추가했다. `Unity.GenerateSceneCodeFromImage`가 `unity command` CLI가 아닌 어시스턴트 도구 체계에 속한다는 점, 그리고 Texture2D 에셋 컨텍스트 경유 호출이 실패한다는 점을 구분하지 못해 생성과 조립을 섞어 시도하는 사례가 있었다.

**v5 변경**: 프리미티브 구조물 + 생성 AI 인물 2체를 한 흐름으로 통합하는 실제 테스트(사막 바 씬)에서 얻은 결과를 반영했다. ① yaw 판정에서 **정사영 탑다운이 항상 최선은 아니다** — 머리카락 실루엣만으로는 정면 판정이 애매했던 사례가 있어, 눈높이 근접 카메라로 여러 yaw 후보를 놓고 비교하는 방법을 보완 절차로 추가했다. 실내에 배치할 때는 지붕 등 상부 구조가 탑다운 시야를 가릴 수 있어 임시로 렌더러를 꺼야 한다는 점도 반영했다. ② 서로 다른 인물 2체(같은 모델 `model3d-tripo-p1`)에서 yaw 오프셋이 동일(270°)하게 나온 실측 — 표본 2개뿐이라 일반 법칙으로 단정하지 않되, 유의미한 데이터포인트로 기록한다. ③ 생성 메시가 프롬프트의 부정 지시를 무시하고 의도치 않은 소품(의자)을 포함시킨 사례 — 배치 계획에 이 가능성을 감안한다. ④ 씬 계층 조작 스크립트가 보고한 오브젝트 개수(직계 자식 카운트)가 개별 named 오브젝트의 실제 존속을 보장하지 않는다는 실측 — 검증은 집계 카운트가 아니라 개별 오브젝트 존재 조회로 한다.

**v4 변경**: 인물 1종을 시트부터 씬 배치까지 실제로 완주하며 세 가지를 반영했다. ① 배경 규약을 검정 → **크로마키 단색**으로 변경(근거는 [ai-generation.md](ai-generation.md) §7). ② **국소 결손을 미달로 판정하지 않는다** — 마스크에 톱니형 결손이 있어도 정상 메시가 나왔다. 이전 판정 기준은 "완전성"만 말해 결손이 곧 미달로 읽혔고, 그 결과 통과 가능한 마스크를 계속 다듬는 낭비가 발생했다. ③ 배치 단계가 절차에 없어 매번 다시 알아내야 했던 값들(누운 축, 정면 오프셋, 키 정규화, 접지, 벽·기둥 접촉, 적용 순서, 수치 판정)을 「씬 배치 규약」으로 신설. 접촉 정규화는 **축에 따라 수단이 갈린다**는 실측이 근거다 — 접지(Y)는 AABB가 회전 편차 0으로 안정적이지만, 수평 접촉에 AABB를 쓰면 yaw에 따라 42% 흔들리고 모자 챙 같은 얇은 돌출물에 15cm 끌려간다. 키 목표값은 표본 부족으로 확정하지 않고 절차만 남겼다.

**v3 변경**: 파이프라인 각 단계에 **사전 조건**을 명시하고 2단계를 두 스텝(시트 생성 + 배경 제거)으로 분리했다. 실제 사례에서 2단계 시트를 3장 만든 뒤에야 3단계가 알파 채널을 강제한다는 사실과 배경 제거 프로바이더가 막혀 있다는 사실을 발견해, 만든 시트가 전부 사용 불가가 됐다. 3단계 산출물이 Prefab이라는 점, 리깅 등 후처리 커맨드가 존재한다는 점(5단계)도 함께 반영했다. 호출 메커니즘은 [ai-generation.md](ai-generation.md)로 분리했고 이 문서는 품질 기준·판단을 담당한다.

## 0. 도구 및 파이프라인 수단 구분 (필수)
- **AI 어시스턴트 도구**: `Unity.GenerateSceneCodeFromImage`는 `unity command` CLI 명령어가 아닌 어시스턴트 도구 체계에 속함.
  - 채팅 메시지에 이미지 파일이 직접 첨부된 경우: `Unity.GenerateSceneCodeFromImage()`로 직접 Three.js 코드 도출 가능.
  - Project 패널의 Texture2D 에셋 컨텍스트(`instance_id`)를 통한 호출: 현재 에디터 파이프라인의 `GetImageAssetContent` API 미지원으로 텍스처 데이터 인출 시 실패함.
- **대응 절차**:
  - Texture2D 에셋 기반 작업 시 생성(`GenerateAssetTool.GenerateAsset`)과 조립(`unity command` / C# RunCommand)을 분리 수행.
  - 이미지 파일 직접 첨부 시 `Unity.GenerateSceneCodeFromImage()` 사용 가능.

## 적용 대상 판단 (프리미티브 vs 3D 생성 모델)
- **레퍼런스 이미지 한 장으로 씬 전체(공간+배치+카메라)를 재구성하는 작업이면 이 판단은
  [scene-from-reference-image.md](scene-from-reference-image.md)가 먼저 다룬다** — 이 절은 그 문서에서
  "생성형"으로 정해진 개별 오브젝트, 또는 씬 재구성이 아닌 개별 에셋 생성 작업에 적용한다.
- 구조/건축 요소(마루, 천장, 벽, 기둥 등 평면·직육면체·단순 형태로 근사 가능한 오브젝트)는 프리미티브(Cube, Plane, Cylinder 등)로 배치 가능.
- 유기적 형태/캐릭터/장식 조형물(나무, 사람, 동물, 조각상 등 프리미티브 조합으로 실루엣·디테일을 원본 의도대로 표현할 수 없는 오브젝트)는 반드시 3D 생성 모델(파이프라인 절)을 거쳐야 함. 프리미티브 조합으로 임의 대체 금지.
- 판단 기준: 해당 오브젝트의 실루엣/디테일을 프리미티브 조합으로 원본 의도 훼손 없이 표현 가능한지 여부. 애매한 경우 진행 전 사용자에게 확인.
- 이 기준을 우회할 목적으로 프리미티브로 먼저 배치한 뒤 "임시"임을 밝히지 않고 완성된 결과물처럼 보고하는 행위는 AGENTS.md §1.2(임의 대체 금지) 위반으로 간주.

## 원칙
- 복잡한 원본 이미지에서 대상을 직접 크롭하여 3D 입력값으로 사용 금지(경계면 잡영, 하반신 누락, 부유물 구워짐 유발).
- 전신 형태 완전성 제약: Full body, head-to-toe, standing pose, complete legs and feet 명시. 배경은 **투명도 검정도 아니라 크로마키 단색**을 요구하고, 투명화는 별도 스텝에서 처리한다 — 구체적 프롬프트 문구와 색 선택 기준은 [ai-generation.md](ai-generation.md) §7. 검정 배경은 모델이 비네트 그라디언트로 그려버려 배경 제거를 어렵게 만든다는 것이 실측으로 확인됐다.
- 상반신만 생성되거나 하반신 누락 시 품질 미달로 판정, 씬 배치 중단. 프레임 테두리에 사지가 닿아 잘린 경우도 동일하게 미달로 판정한다.
- 반대로 **국소 결손은 미달이 아니다.** 마스크 실루엣에 10~15px 톱니형 결손이 있어도 정상 메시가 나온 실측이 있다. 판정 기준은 [ai-generation.md](ai-generation.md) §8의 4개 항목이며, 통과하면 다듬기를 멈추고 다음 단계로 간다.

## 파이프라인

각 단계의 **사전 조건**을 착수 전에 확인한다. 뒤 단계에서 막히면 앞 단계 산출물이 통째로 무용지물이 된다. 호출 방법·파라미터는 [ai-generation.md](ai-generation.md)를 따른다.

0. 입력 이미지 사전 판단: 레퍼런스 이미지가 이미 배경과 분리된 단일 피사체의 깨끗한 전신 이미지라면 1~2단계를 건너뛰고 3단계로 직행. 배경과 인물이 겹쳐 있거나 뒤섞인 복합 이미지일 때만 1~2단계 필수.
1. 대상 분석 및 프롬프트화: 성별, 의상, 외형, 색상 스타일 추출. 배경/장식물/무관 요소 제외.
2. 2D 전신 시트 생성 — **두 스텝이다**:
   - 2a. `GenerateSprite`로 전신 시트 생성. Full body, head to toe, front view, standing pose, 절단 없이 온전한지 확인. **배경은 크로마키 단색으로 지정한다**([ai-generation.md](ai-generation.md) §7) — 여기서 배경을 잘못 지정하면 2b가 막혔을 때 복구 비용이 커진다.
   - 2b. `RemoveImageBackground`로 배경 제거. **생성 프롬프트에 "transparent background"를 넣는 것으로는 대체되지 않는다** — 알파가 아니라 체커보드 무늬가 그려진다.
   - **사전 조건**: 2b는 외부 프로바이더(Photoroom)에 고정되어 있다. 쿼터가 막혀 있으면 3단계로 진행할 수 없으므로, **시트를 만들기 전에 가용성을 먼저 확인한다** — 절차는 [ai-generation.md](ai-generation.md) §5의 사전 프로브(더미 128×128, 포인트 0, 약 19초). 막혀 있으면 AGENTS.md §1.4로 보고·정지하고, 승인 시 [ai-generation.md](ai-generation.md) §10으로 진행한다.
3. Image-to-3D Mesh 변환: 2단계 결과물(또는 0단계에서 재사용 판정된 이미지)을 레퍼런스로 `GenerateMesh` 실행(waitForCompletion=true).
   - **사전 조건**: 레퍼런스 이미지에 **실제 알파 채널이 있어야 한다.** 단색·검정 배경은 거부된다("must have a transparent background"). 알파 0 픽셀 비율로 사전 확인할 것.
   - **산출물**: 원시 메시 파일이 아니라 **메시와 머티리얼이 포함된 self-contained Prefab**이다. `meshFormat`이 `glb`이면 `com.unity.cloud.gltfast`가 설치돼 있어야 임포트된다.
4. 메시 품질 검증(배치 전 필수):
   - 사지 누락 여부(Bounds Y-Extent, 하단 절단면 확인)
   - 아티팩트 합성 여부(배경/장식물 구워짐 확인)
   - 접지 및 포즈 상태(발끝 정방향 지면 배치 가능 여부)
   - **의도치 않은 소품이 구워졌는지(실측).** 시트 생성 프롬프트에 "의자 없이"처럼 명시해도 모델이 의자를 포함시킨 사례가 있다(부정 지시 신뢰 불가, [ai-generation.md](ai-generation.md) §7). 구워진 소품이 있으면 그 자리에 이미 놓아둔 프리미티브 소품과 중복·충돌하는지 확인하고, 어느 쪽을 쓸지 결정한다(생성물의 소품을 쓰고 프리미티브를 치우는 쪽이 대개 간단하지만 재질·색이 어긋날 수 있다).
5. 후처리(필요할 때만): `RigMesh`(리깅), `TextureMesh`(텍스처 추가), `RetopologyMesh`(토폴로지 개선). 생성 메시가 리깅되지 않았다는 이유로 포즈를 프리미티브·회전 근사로 대체하기 전에 이 단계를 먼저 검토한다.

## 씬 배치 규약 (Tripo P1 / fbx 실측)

**적용 범위**: 아래 수치(정면 오프셋 270° 등)는 `model3d-tripo-p1` 산출물 고유의 실측값이라 다른 생성기·
오브젝트에 그대로 쓸 수 없다. 하지만 **"생성 메시의 로컬 정면 축은 알 수 없고, 실측·검증 없이는 정면
방향을 가정할 수 없다"는 원칙 자체는 생성기·오브젝트 종류와 무관하다** — 인물뿐 아니라 소파·가전 등
방향성이 있는 모든 생성 메시에 동일하게 적용된다. 실패 사례([scene-from-reference-image.md](scene-from-reference-image.md)
§5): 로컬 TRELLIS2로 생성한 소파를 "나중에 스크린샷으로 확인하겠다"고만 적어두고 실제 yaw 후보 검증
없이 identity 회전으로 배치해, 180도 뒤집힌 채로 완료 보고했다.

생성 프리팹은 그대로 놓으면 눕고, 크기도 접지도 맞지 않는다. 아래 값은 `model3d-tripo-p1` + `meshFormat: fbx` 산출물(정점 3295, 키 1.66m로 스케일)에서 실측한 것이다.

### 1. 자세 · 크기

- **누워서 임포트된다.** 원시 렌더러 바운즈가 `(0.3496, 0.3457, 0.9980)` — 장축이 **Z**다(FBX Z-up 유지). `eulerAngles = (270, yaw, 0)`으로 세운다. Unity의 오일러 적용 순서상 이 형태는 "Rx(−90)로 세운 뒤 월드 Y로 yaw"가 되므로 `yaw` 성분만 방위로 쓰면 된다.
- **정면은 +Z가 아니다.** 모델 로컬 정면 축은 임의이므로 `yaw`를 원하는 방위로 그대로 넣으면 등을 돌린다. 프로젝트마다 **오프셋을 한 번만 실측해 매니페스트에 상수로 기록하고 재사용한다.** 측면 뷰로 눈대중하면 오차가 크다(실측: 측면 뷰 추정으로 계산한 yaw가 맞지 않았다).
  - **정사영 탑다운이 항상 최선은 아니다(실측, 예외 사례).** 머리 위에서 내려다보면 머리카락 덩어리만 보여 정면/후면 판정이 애매한 경우가 있었다. 이때는 **눈높이 근접 카메라를 세우고 yaw 후보(0/90/180/270 등)를 하나씩 대입해 스크린샷으로 비교**하는 방법이 더 명확했다 — 선글라스·이목구비·앞판 디테일이 직접 보이므로 판정이 쉽다.
  - **실내에 배치할 때는 지붕·천장이 탑다운 시야를 가릴 수 있다.** 캐릭터가 지붕 아래에 있으면 탑다운 카메라가 지붕 표면만 찍는다 — 지붕 등 상부 구조의 렌더러를 임시로 `enabled = false`로 끄고 촬영한 뒤 반드시 다시 켠다.
  - **같은 모델의 yaw 오프셋이 인물마다 같을 수 있다(약한 근거).** `model3d-tripo-p1`로 만든 서로 다른 인물 2체가 이번 테스트에서 공교롭게 둘 다 270°로 일치했다. 표본 2개뿐이므로 다음 인물에도 동일할 것으로 가정하지 말고, 매번 위 방법으로 재확인한 뒤 결과가 같으면 그때 문서에 프로젝트 상수로 반영한다.
- **키 정규화 — 절차는 확정, 목표값은 미확정.** 장축 길이가 대략 1.0으로 나오므로(실측 0.9980) `scale = 목표키 / 실측높이`를 세운 **뒤에** 바운즈를 다시 재서 적용한다. 다만 **목표키를 무엇으로 잡을지는 아직 표본이 부족하다** — 사례가 더 쌓일 때까지 프로젝트별로 지정하고, 이 문서에 고정 상수로 박지 않는다.
- **기존 씬 오브젝트의 크기를 기준으로 삼지 않는다.** 매니페스트의 스케일 규약(예: 1u = 1m 실척)을 기준으로 한다. 실측 사례 — 먼저 배치돼 있던 인물이 키 1.00m로 규약(1.7m)에서 벗어나 있었고, 그 값에 맞추면 오차가 누적된다. 불일치를 발견하면 규약대로 배치하고 기존 오브젝트의 불일치를 보고한다.

### 2. 접지 — AABB를 그대로 쓴다

`y -= bounds.min.y`로 `minY = 0`을 만든다. 피벗이 중심에 있어 좌표를 그대로 쓰면 반쯤 묻히거나 뜬다.

이 축에서만 AABB가 신뢰할 수 있다는 근거(실측):

| 확인 항목 | 값 |
|---|---|
| yaw 0~315° 8종에서 `bounds.min.y` | 전부 `0.0000` (편차 0) |
| yaw 8종에서 바운즈 높이 | 전부 `1.6600` (편차 0) |
| `bounds.min.y` vs 정점 p2 차이 | `0.0162` (1.6cm) |

발바닥이 넓은 평면이라 절대 최저점이 질량의 최저점과 사실상 일치하고, 중력 방향이 축정렬이라 회전에도 흔들리지 않는다.

### 3. 벽 · 기둥 접촉 — AABB를 쓰지 않는다

생성 메시의 **수평** 접촉면을 AABB min/max로 잡으면 두 가지가 깨진다.

- **회전에 42% 흔들린다.** 같은 오브젝트의 AABB 폭이 `yaw=0`에서 `x=0.5815`, `yaw=45`에서 `x=0.8178`. AABB 면을 벽에 스냅하면 **방위만 바꿔도 최대 12cm 이동한다.**
- **얇은 돌출물에 끌려간다.** `AABB − 정점 p2` 여유가 X축 `0.1515 / 0.1415`, Z축 `0.0749 / 0.0754`. X쪽 15cm는 모자 챙이다. AABB를 벽에 붙이면 챙만 닿고 **몸통이 15cm 떠 있게 된다.**

대신 아래를 쓴다.

- **접촉면은 정점 백분위 `p2` / `p98`** (월드 좌표, 접촉 축 기준). 얇은 돌출물과 부유 잡점을 배제하면서 질량을 대표한다.
- **접촉 평면은 높이 구간이 겹치는 장애물 중 가장 안쪽으로 나온 표면**을 고른다. 벽면은 하나의 평면이 아니다 — 실측: `Wall_L_DoorSide`는 `x[-0.120, 0.000] y[0, 4.000]`이지만 `Wainscot_L`이 `x[0.000, 0.060] y[0, 1.150]`으로 아래쪽에서 6cm 더 튀어나온다. 1.66m 인물은 두 구간에 걸치므로 단일 평면으로 스냅하면 웨인스콧을 파고들거나 상단 벽에서 뜬다. 구간별로 나누지 말고 보수적으로 가장 돌출된 면(위 예에서 `x = 0.060`) 하나를 쓰는 편이 단순하고 관통이 없다.
- **여유 1cm를 남긴다.** 정확히 0으로 붙이면 z-fighting과 그림자 누출이 생긴다.

**예외 — 박스형 프리미티브 소품(카트, 세면대, 받침대 등)은 AABB 그대로 써도 된다.** 축정렬 직육면체라 AABB가 실제 형상과 일치한다. 백분위·구간 평면이 필요한 대상은 생성된 유기적 메시뿐이다.

### 4. 적용 순서를 고정한다

**세우기 → 스케일 → yaw 확정 → 접지 → 수평 접촉.**
AABB가 yaw에 42% 흔들리므로 **yaw를 확정하기 전에 수평 접촉을 계산하면 무효가 된다.** 스케일도 접지보다 먼저 와야 한다(스케일이 `min.y`를 바꾼다).

### 5. 배치 후 수치 판정

AGENTS.md §3.2대로 스크린샷 눈대중으로 판정하지 않는다.

| 판정 항목 | 합격 기준 |
|---|---|
| 접지 | `\|bounds.min.y - 바닥높이\| <= 0.002` |
| 관통 | 오브젝트 정점 중 장애물 AABB 내부에 든 개수가 **0** |
| 키 | 프로젝트가 지정한 목표키와 `bounds.size.y` 일치 |

## 씬 배치 후 검증
- **오브젝트 개수 집계만으로 구조 무결성을 확신하지 않는다(실측).** 배치 스크립트가 보고한 "직계 자식 N개" 같은 집계 카운트는 하위 개별 오브젝트가 실제로 존속하는지까지 보장하지 않는다 — 동일 세션에서 생성 직후 스크린샷으로는 존재가 확인된 오브젝트 2개가, 이후 다른 시점의 계층 조회에서는 원인 불명으로 사라져 있던 사례가 있었다(어느 호출에서 유실됐는지 특정하지 못함). 중요한 개별 오브젝트는 `get_scene_hierarchy` 또는 `find_gameobjects`로 이름을 직접 조회해 존재를 확인한다.
- 결과물이 벽/다른 오브젝트에 가려지지 않고 명확히 보이는 각도를 최소 1개 이상 찾아 스크린샷 캡처 후 검증.
- 정면/측면/조감도는 참고용 기본값일 뿐 고정 필수값이 아님 — 씬 구조상 특정 각도가 가려진다면 생략하고, 결과를 실제로 판별 가능한 각도를 우선.
- 검증 목적은 "여러 각도를 찍었는가"가 아니라 "찍은 스크린샷으로 결과물의 정상 여부를 실제로 판단할 수 있는가"임.
